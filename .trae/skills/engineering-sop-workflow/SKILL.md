# Engineering SOP Workflow

本 Skill 用于在任何软件工程任务中**新增功能 / 优化重构 / 修 Bug / 跨模块联动**时强制走一套**标准流程**，避免遗漏、返工、未验证就交付。

---

## 何时触发

满足下列任一条件时，**立即调用**本 Skill：

1. 用户要求"新增 / 添加 / 创建"一个功能、模块、接口、服务
2. 用户要求"优化 / 重构 / 改造 / 调整"现有代码的行为、性能、架构
3. 用户报告 Bug 并希望修复
4. 用户要求跨模块联动（如"前端 + 后端"、"服务 A + 服务 B"）
5. 用户要求"调整接口签名 / 数据结构 / 核心逻辑 / 默认行为"

> ❌ 不触发：纯改文案、复制粘贴、查询代码、写文档、纯样式微调（单行 CSS / 单属性）。

---

## 标准流程（8 步）

### ① 理解需求（必做）

用**业务语言**复述用户需求，包含：

- **场景**：在哪个模块 / 哪个服务 / 用户操作路径是什么
- **目标**：用户希望达到什么效果
- **约束**：性能约束、兼容性约束、不能动什么、必须保留什么
- **边界**：哪些情况算"已完成"、哪些情况不在本次范围内

⚠️ 复述完之后必须明确问用户："**我这样理解对吗？**"。

### ② 现状摸排（必做）

不要凭印象动手，先查：

- `Read` 目标文件，理解现有结构（函数签名、类型定义、数据流）
- `Grep` 相关链路：找出"上游怎么传进来 → 当前模块处理 → 下游怎么消费"
- `Grep` 是否有同类已存在的模块、工具函数、库可复用（**禁止重复造轮子**）
- 检查依赖：相关模块、中间件、Store、API 客户端的当前签名

产出：**一份"现状代码地图"**，包含关键文件路径 + 关键函数行号引用。

### ③ 方案设计 + ⚠️ 强制确认（必做）

输出**方案文档**，至少包含：

1. **核心改动一句话**（一句话说明白做什么）
2. **详细分解**：按文件列出每个文件的具体改动点
3. **预期效果**：用 ✅ 列出"完成后会变成什么样"
4. **改动文件清单**：表格列出 `文件 | 改动`
5. **待确认问题**：所有不确定的设计选择、技术选型，用 `AskUserQuestion` 让用户拍板

🚨 **强制规则**：方案输出后**必须等用户回复"开始 / 确认 / 同意"再动手**。

如果是显而易见的极小改动（< 5 行），可以省略方案，但仍需口头说一句"我要改 X 文件的 Y 行"。

### ④ 拆任务（推荐）

用 `TodoWrite` 把方案拆成 3-6 个**原子任务**：

- 每个任务对应一个文件 / 一个独立修改点
- 任务粒度不宜过细（避免噪音），也不宜过粗（避免一锅烩）
- 严格遵循"一次只有一个 in_progress"

### ⑤ 逐项实现

实现时遵循：

- 优先 `SearchReplace`（精确小步），避免 `Write` 覆盖整文件
- **每次只改一处**：改完一处再改下一处，便于回滚
- **顺手清理**：未用变量删除、重复计算合并、可复用的逻辑提到公共层
- **遵循现有代码风格**：先看相邻代码的 import 风格、命名风格、错误处理风格
- **不擅自加注释**：除非用户要求或必须解释的复杂逻辑
- **不擅自创建新文件**：能改现有文件就不新建

### ⑥ 验证（必做，按项目实际工具选择）

按以下顺序检查，**不能跳过**：

1. **Lint / 代码风格检查**（必跑）
   - 前端：`npx eslint <修改的文件路径>`
   - Python：`ruff check <修改的文件路径>`
   - Go：`golangci-lint run <修改的文件路径>`
   - 其他语言按项目实际 Lint 工具执行
   - 要求：**0 错 0 警告**（已存在的预存警告除外，需明确指出）

2. **类型检查**（项目使用类型系统时必跑）
   - TypeScript：`npx tsc --noEmit` 或 `npm run typecheck`
   - Python / mypy：`mypy <修改的文件路径>`
   - 其他语言按项目实际类型检查工具执行

3. **单元测试 / 集成测试**（项目有相关测试时必跑）
   ```bash
   npm test -- <相关文件>
   # 或 npx jest <pattern>
   # 或 npx vitest run <pattern>
   # 或 go test ./...
   # 或 pytest <path>
   ```

4. **构建检查**（必要时）
   - 改动涉及构建配置、入口、依赖变更时
   - `npm run build` / `go build` / `cargo build` 等对应命令

### ⑦ 不能自动验证的部分 → 明确告知用户（必做）

🚨 **重要原则**：以下情况**必须告诉用户"我无法替你测试，请手动验证"**：

- 浏览器 UI 行为（hover、点击、动画、响应式）
- 与真实后端 / 第三方 API / 数据库的联调
- 涉及登录态、权限、Cookie、Session、Token 的请求
- 跨浏览器 / 跨平台兼容性
- 性能表现（FPS、首屏时间、QPS、延迟）
- 视觉效果（颜色、布局是否符合预期）
- 基础设施变更（Docker、K8s、CI/CD 配置）

❌ **禁止**：假装"已测试通过"或"应该没问题"。
✅ **要做**：给出**手测清单**（见步骤 8）。

### ⑧ 总结 + 手测清单（必做）

最后给用户：

1. **改动总结**：每个文件做了什么、为什么这么做
2. **验证结果**：Lint / 类型检查 / 测试的实际结果
3. **手测清单**：用 ✅ 列表给出**用户可逐条勾选的步骤**，例如：
   ```
   ✅ 调用 GET /api/orders → 返回结果应包含新字段 payment_status
   ✅ 打开订单详情页 → 已结算行应自动勾选
   ✅ 点表头全选 → 已结算行不参与切换
   ```

## 跨模块联动场景的额外规则

当任务涉及**多个模块 / 服务 / 前后端联动**时：

1. **方案阶段必须画出数据链路**：`上游字段 X → 传输格式 → 下游字段 Y → 持久化 → 响应 → 消费端字段 Z`
2. **字段命名核对**：命名风格转换点要明示（如 snake_case ↔ camelCase、Proto ↔ JSON）
3. **各模块验证步骤同样必须有**：各自的编译、Lint、单测、必要时构建
4. **关注现有的权限过滤 / 租户隔离**：新接口 / 新功能要不要按用户隔离？
5. **批量优先**：能批量查就别 N+1，注意跨模块调用的性能边界

## 经典反例（要避免）

- ❌ 没看现状直接改 → 重复造轮子或破坏现有逻辑
- ❌ 方案没确认就动手 → 用户说"不是我要的方向"返工
- ❌ 一次改一大堆文件 → 出错难定位、回滚困难
- ❌ 改完没跑 Lint 就报"完成" → 用户拉下来构建失败
- ❌ 把"我应该测过了"等同于"已测试" → 实际从未运行的交互逻辑
- ❌ 擅自新增 README/文档/示例文件 → 污染仓库

## 标准产出模板

每次任务的最终消息应包含以下结构（缺一不可）：

```
## 改动总结
- 📁 文件 1：xxx
- 📁 文件 2：xxx

## 验证
- Lint：0 错 0 警告
- 类型检查：通过
- 测试：xx/xx 通过

## ⚠️ 需你手动测试
- ✅ 步骤 1
- ✅ 步骤 2
- ✅ 步骤 3
```

## 最后

**本流程的核心精神**：**慢即是快**。先想清楚、和用户对齐，再下笔。验证完整、边界清楚，才算交付。
